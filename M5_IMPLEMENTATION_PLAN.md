# M5 Implementation Plan

## Milestone

M5: Persistent Combat API

## Status

Preparation completed.

All blocking decisions D1-D20 in `M5_SOURCE_AUDIT.md` are approved.

Production implementation may begin.

## Objective

Connect the pure M4 combat engine to authenticated HTTP endpoints and persistent PostgreSQL combat sessions.

M5 must allow a player to:

1. Start an eligible combat.
2. Pay the Energy cost exactly once.
3. Retrieve the active combat session.
4. Submit one combat action for the expected turn.
5. Persist the resulting state and ordered events atomically.
6. Retrieve a specific combat session.
7. Retrieve the ordered event log.
8. Continue an active combat after an application restart.

## Required endpoints

```http
POST /characters/:characterId/combat
GET /characters/:characterId/combat
GET /characters/:characterId/combat/:combatSessionId
POST /characters/:characterId/combat/actions
GET /characters/:characterId/combat/:combatSessionId/log
```

All endpoints require authentication and character ownership.

## Combat-start request

```ts
{
  monsterCode: string;
}
```

The client does not provide:

- character statistics,
- monster statistics,
- Energy cost,
- initial Health,
- eligibility results,
- timestamps,
- random values,
- combat status.

## Combat-action request

```ts
{
  expectedTurn: number;
  action: {
    type: "basic_attack";
  };
}
```

The action endpoint always resolves the character's current active combat session.

The client does not provide a combat session ID in the request body.

## Combat response

Combat start and combat action return the current session view:

```ts
{
  combatSessionId,
  characterId,
  monsterCode,
  status,
  defeatReason,
  currentTurn,
  player: {
    currentHealth,
    maximumHealth,
    attack,
    defense
  },
  monster: {
    currentHealth,
    maximumHealth,
    attack,
    defense
  },
  startedAt,
  endedAt,
  events
}
```

For start and action operations, `events` contains only events generated by the current request.

The complete event history is returned by the dedicated log endpoint.

## Architectural rules

### M4 boundary

The M4 combat domain remains pure.

M4 must not depend on:

- PostgreSQL,
- HTTP,
- authentication,
- repositories,
- sessions,
- application configuration,
- `Clock`,
- production randomness,
- persistent identifiers.

M5 is responsible for:

- loading persistent state,
- reconstructing the M4 `CombatState`,
- supplying `RandomSource`,
- calling `resolveCombatAction`,
- mapping the returned state,
- persisting ordered events,
- handling transactions and concurrency.

### Trusted server data

The server is authoritative for:

- character ownership,
- character resources,
- effective character statistics,
- monster definitions,
- monster eligibility,
- Energy costs,
- timestamps,
- randomness,
- combat results,
- persistent session state.

The client must never author these values.

## Out of scope

M5 does not implement:

- Experience rewards,
- Gold rewards,
- loot generation,
- item generation,
- character level changes,
- death Experience penalties,
- Blessing consumption,
- monster cooldown writes,
- Bestiary writes,
- kill statistics,
- Task Boss progression,
- final combat-log retention,
- player spells,
- monster abilities,
- consumables,
- active combat effects,
- multiple targets,
- escape actions,
- abandonment actions.

## Phase 2: Schema migration

### Objective

Create the persistent schema required to reconstruct M4 combat state and store ordered events.

### Migration number

Create a new tracked migration after migration `087`.

Expected filename direction:

```txt
088_persistent_combat_api.sql
```

The final name should describe the actual schema changes.

### Extend `combat_sessions`

Add snapshots required by M4.

Character snapshot:

```txt
character_maximum_health
character_attack
character_defense
```

Monster snapshot:

```txt
monster_maximum_health
monster_attack
monster_defense
```

Add:

```txt
defeat_reason
```

Current values continue to use:

```txt
character_health
monster_health
current_turn
status
started_at
ended_at
```

### Snapshot constraints

Require:

- maximum Health values greater than `0`,
- Attack and Defense values greater than or equal to `0`,
- current Health values between `0` and snapshotted maximum Health,
- current turn between `1` and `100`.

### Status and defeat-reason constraints

Supported database statuses remain:

```txt
Active
Victory
Defeat
Abandoned
```

M5 produces only:

```txt
Active
Victory
Defeat
```

Rules:

- `Active` requires `ended_at IS NULL`,
- `Active` requires `defeat_reason IS NULL`,
- `Victory` requires `ended_at IS NOT NULL`,
- `Victory` requires `defeat_reason IS NULL`,
- `Defeat` requires `ended_at IS NOT NULL`,
- `Defeat` requires a valid defeat reason.

Allowed defeat reasons:

```txt
PlayerHealthDepleted
TurnLimitExceeded
```

The existing `Abandoned` state remains compatible with existing schema history but is not produced by M5.

### Create `combat_session_events`

Required columns:

```txt
combat_session_event_id
combat_session_id
turn_number
event_order
event_type
event_data_json
created_at
```

Required rules:

- event session must exist,
- event turn must be between `1` and `100`,
- event order must be non-negative or positive according to the selected convention,
- event data must be JSONB,
- one event position must be unique within a session and turn.

Recommended uniqueness:

```txt
UNIQUE (
  combat_session_id,
  turn_number,
  event_order
)
```

Recommended retrieval index:

```txt
INDEX (
  combat_session_id,
  turn_number,
  event_order
)
```

### Migration tests

Verify:

- migration applies successfully,
- migration status reports no pending migrations,
- snapshot constraints reject invalid values,
- session status and defeat reason remain consistent,
- duplicate event order is rejected,
- event rows are deleted with the session if that remains the approved foreign-key behavior,
- one character still cannot have multiple active sessions.

### Exit criteria

```powershell
npm run db:migrate
npm run db:migrate:status
npm run db:test
```

Expected:

- 88 migrations applied,
- 0 pending migrations,
- PostgreSQL connection successful.

## Phase 4: Production RandomSource

### Objective

Provide server-controlled production randomness for M4.

### Requirements

Implement `RandomSource` using `node:crypto`.

The implementation must satisfy:

```ts
0 <= nextFloat() < 1
```

and:

```ts
minimum <= nextInt(minimum, maximum) <= maximum
```

Both integer bounds are inclusive.

### Validation

The implementation must reject invalid input such as:

- non-safe integer bounds,
- minimum greater than maximum,
- ranges unsupported by the selected crypto API.

### Security boundary

The client must not provide:

- seeds,
- rolls,
- random bytes,
- damage results,
- hit results.

### Tests

Cover:

- float lower bound,
- float upper exclusivity,
- inclusive integer minimum,
- inclusive integer maximum,
- equal integer bounds,
- invalid range rejection.

Tests must not depend on one specific random outcome.

### Exit criteria

- implementation satisfies the M4 `RandomSource` contract,
- no `Math.random()` is used,
- tests are stable and non-flaky.

## Phase 6: Transactional combat start

### Objective

Start a fight atomically and deduct Energy exactly once.

### Transaction flow

1. Read `observedAt` once from `Clock`.
2. Begin transaction.
3. Lock the owned active character with `FOR UPDATE`.
4. Reject missing, archived, or foreign characters.
5. Reject an existing active combat session.
6. Apply resource regeneration using `observedAt`.
7. Load the monster by stable code.
8. Load all monster data required by combat start.
9. Revalidate monster eligibility.
10. Reject zero character Health.
11. Validate available Energy.
12. Calculate effective character statistics inside the transaction.
13. Validate player statistics.
14. Validate monster statistics.
15. Deduct Energy exactly once.
16. Insert the active combat session with snapshots.
17. Commit.
18. Return the new session view with an empty current-operation event list.

### Character lock

The character query must confirm:

- account ownership,
- active character status,
- current resources,
- regeneration fields.

The lock must occur before checking existing active combat and before deducting Energy.

### Statistics snapshot

Player snapshot comes from the authoritative M2 calculator.

Monster snapshot comes from the current persistent monster definition.

Do not use client-provided data.

### Eligibility

Revalidate:

- level,
- cooldown,
- Task Boss state,
- Daily Boss rotation,
- Daily Boss attempts.

Reuse existing domain rules where possible.

Do not reuse a repository design that prevents all reads from participating in the same transaction.

### Failure behavior

Any failure must roll back:

- regeneration writes,
- Energy deduction,
- session creation.

### Unit tests

Cover:

- successful combat start,
- start with partial Health,
- start after Energy regeneration,
- zero Energy cost,
- insufficient Energy,
- zero Health,
- unknown monster code,
- ineligible monster,
- existing active combat,
- foreign character,
- archived character,
- statistics snapshot creation,
- single `Clock.now()` call.

### Integration tests

Cover:

- Energy deducted exactly once,
- session created with correct snapshots,
- failed start leaves Energy unchanged,
- failed start creates no session,
- concurrent starts create one active session,
- concurrent starts deduct Energy once,
- session survives repository recreation.

### Exit criteria

Combat start is transactional, recoverable, ownership-safe, and concurrency-safe.

## Phase 7: Transactional combat action

### Objective

Resolve one expected turn and persist the result atomically.

### Transaction flow

1. Read `observedAt` once from `Clock`.
2. Begin transaction.
3. Lock the character's active session using `FOR UPDATE`.
4. Validate account and character ownership.
5. Validate that the session remains active.
6. Compare `expectedTurn` with `current_turn`.
7. Reconstruct M4 `CombatState`.
8. Call `resolveCombatAction`.
9. Map the resulting state to persistent status.
10. Update current Health, turn, status, defeat reason, and `ended_at`.
11. Insert ordered events.
12. Synchronize `characters.current_health` if combat ended.
13. Commit.
14. Return the new session view and current-operation events.

### Expected-turn behavior

If:

```ts
expectedTurn !== currentTurn
```

throw:

```txt
COMBAT_TURN_MISMATCH
```

Do not:

- call M4,
- update the session,
- insert events,
- synchronize Health.

### Event persistence

For every M4 event, persist:

- the turn being resolved,
- its zero-based or one-based order according to one documented convention,
- event type,
- complete event JSON,
- `observedAt`.

The event order must match the array returned by M4.

### Terminal behavior

Map:

```txt
PlayerVictory -> Victory
PlayerDefeat  -> Defeat
```

On terminal state:

- preserve the final round number,
- set `ended_at = observedAt`,
- write defeat reason where required,
- synchronize final character Health.

Do not grant rewards or apply death penalties.

### Unit tests

Cover:

- successful continuing round,
- player victory,
- player defeat through Health depletion,
- player defeat through turn limit,
- stale expected turn,
- missing active session,
- already-ended session,
- event order,
- terminal Health synchronization,
- no character Health synchronization while active,
- one `Clock.now()` call,
- injected RNG usage.

### Integration tests

Cover:

- state persists after action,
- events persist in order,
- session and events roll back together,
- two concurrent requests cannot resolve the same turn,
- stale second request returns turn mismatch,
- terminal Health is synchronized atomically,
- completed combat no longer appears as active.

### Exit criteria

One turn cannot be executed twice, and state plus events remain atomic.

## Definition of Done

M5 is complete only when all conditions below are satisfied.

### Persistence

- Combat sessions persist across application restarts.
- All statistics required by M4 are snapshotted.
- Current Health and turn persist after every action.
- Ordered combat events persist atomically with session updates.
- Terminal status and defeat reason persist correctly.

### Combat start

- Ownership is enforced.
- Character row is locked.
- Existing active combat is rejected.
- Resource regeneration occurs before validation.
- Positive Health is required.
- Monster eligibility is revalidated.
- Energy is deducted exactly once.

### Combat actions

- Active session is locked.
- `expectedTurn` is required.
- Stale turns are rejected.
- M4 resolves the action.
- Session state and events are written atomically.
- Concurrent actions cannot resolve the same turn twice.
- Terminal Health synchronizes to the character.
